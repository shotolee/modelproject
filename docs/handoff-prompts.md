# 交接提示词

在项目目录中使用。你只需替换自然语言需求，不需要编写详细规格。每段独立使用；OpenCode 阶段手动选择对应模型。

## 开始：把想法交给 Codex

```text
我想做的项目是：<描述项目、使用者、主要功能与限制，可以分批补充>。
这次先做：<可以暂时不确定>。

请把我的想法整理到 docs/requirements/product.md。
只写产品目标、能力、约束与范围，不要求我提供详细规格或拆分需求文件。
不确定的业务规则列为待确认问题，只追问影响当前工作的关键事项。
这一轮先整理需求，不设计架构、不编码。
```

大需求可先用这段逐步整理；需求已经清楚时可以直接使用下一段，让 Codex 同时整理文档并设计，无需额外审批步骤。

## 1. Codex：设计与计划

```text
本轮目标：<用自然语言说明要做什么，或引用 product.md 的功能名称>。
先不要编写业务代码。

读取 AGENTS.md、docs/requirements/product.md、docs/requirements/change-log.md，
以及现有代码和设计文档。必要时根据我的明确要求整理产品文档，保留业务意图。

请你负责功能细化、流程、模块、数据和接口设计，更新 docs/architecture.md；
在 docs/implementation-plan.md 写明本轮步骤、文件、完成标准、验证方法和不做的范围；
重要技术选择写入 docs/decisions.md。
不要让我先写详细规格，不额外建立需求编号、版本清单或追踪表。
遇到影响业务行为的歧义再向我澄清，常规技术实现由你判断。

旧计划及报告尚未保存时先保留历史，新任务重置评审和审计结论。
本轮计划完整且无阻塞后设为 Ready，记录实施前 Git 评审起点；
新仓库无提交时注明评审全部初始文件。完成后停止，不进入实施。
```

## 日后新增或调整功能

```text
我要新增 / 调整：<描述希望发生的变化，以及原因>。
请同步 docs/requirements/product.md，在 change-log.md 简记日期、重要变化和原因。
分析对已有功能、架构和数据的影响，更新 architecture.md、implementation-plan.md，
必要时更新 decisions.md。具体功能拆分、设计和验证由你完成。
不要改变我的业务意图，先完成设计和计划，不编码。
```

用户也可直接编辑 product.md，然后让 Codex 按本次差异完成上述工作。实施中出现需求变化，先暂停受影响部分、保留已有结果，再更新计划，不混用新旧范围。

## 2. OpenCode + MiniMax M3：实施

```text
你只负责 implementation。
读取 AGENTS.md、docs/requirements/product.md、docs/requirements/change-log.md、
docs/architecture.md、docs/implementation-plan.md、docs/decisions.md。
检查 Git 状态与现有代码，确认计划为 Ready，然后严格按本轮范围实施。
不修改业务要求、架构、验收标准，不做计划外重构。
每个有意义的阶段运行相关检查，在计划中记录修改文件、实际命令和结果。
遇到需求或设计冲突，暂停受影响部分并交回 Codex 判断，不自行重新设计。
完成后总结结果、未验证项和遗留问题，将计划设为待评审并停止。
```

## 3. OpenCode + Kimi：独立评审

```text
你是独立 reviewer，不修改代码，只写 docs/review-report.md。
读取 AGENTS.md、产品需求、架构、计划和决策，检查本轮全部变化与测试证据。
覆盖 Git 起点以来的变化、暂存、未暂存和未跟踪文件；无起点则检查全部初始文件。
直接核对产品意图与本轮范围，不只检查计划是否完成。
关注正确性、遗漏、边界、回归、错误处理、安全、测试及不必要复杂度。
按 Critical / Major / Minor / Suggestion 输出问题、位置、证据、影响和建议，
用功能名称或文档章节说明关联，不需要需求编号。
写明实际评审范围和未验证项；修复后复核再关闭问题。完成后停止。
```

普通实现问题交 MiniMax 修复后再复核，设计或需求冲突交 Codex。建议项不自动扩大本轮范围。

## 4. Codex：终审

```text
读取 AGENTS.md、产品需求、架构、计划、决策及 review-report.md，进行最终审计。
核对当前变化、测试结果以及评审后修改是否已复核。
判断本轮产品意图、架构边界、技术债、复杂度、文档一致性和问题处置。
在 docs/audit-report.md 给出结论，不直接重写代码。
本轮验证完成且无阻塞时将计划设 Done，否则说明需要修复、回设计或补充的证据。
不要把部分实现当成整个产品完成，不自动提交、推送或部署。
```
